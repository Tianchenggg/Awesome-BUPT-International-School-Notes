**1.1.7.1 A Cloud Database Engineer (CDBE) is testing Amazon DynamoDB NoSQL database by reading 200 items of 100 KB (Kilobytes) in size every 2 minutes using Eventual Consistency strategy. The CDBE also tested writing 300 items that are 28 KB (Kilobytes) in size every 1 minute using ordinary, non-transactional writes. (Strong/eventual consistency is a read option.)**

**i) Calculate the Read Capacity Units (RCUs) for the DynamoDB NoSQL database to test the performance of reading from tables in the database.**

**ii) Calculate the Write Capacity Units (WCUs) for the DynamoDB NoSQL database to test the performance of writing to tables in the database.**

Each 100 KB item contains $`\lceil 100/4\rceil=25`$ read-capacity blocks. An eventually consistent read consumes half as much as a strongly consistent read.

```math
\mathrm{RCU}=\frac{200}{2\times60}\times\left\lceil\frac{100}{4}\right\rceil\times\frac12 =20.8333\ldots
```

With evenly spread reads, provision at least **21 RCUs** for this average rate; bursts may require more capacity.

**ii)** Write Capacity Units

```math
\mathrm{WCU}=\frac{300}{60}\times\left\lceil\frac{28}{1}\right\rceil=140.
```

**iii)** Availability

Using the values in the question, MTTF = 100 days = 2,400 hours and MTTR = 200 hours:

```math
A=\frac{2400}{2400+200}=\frac{12}{13}\approx\boxed{92.3077\%}.
```

Capacity units count operations **per second**, not the number of seconds in the interval. See [DynamoDB read/write capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html).

#### 1.1.8 Describe the main differences between distributed computing and parallel computing systems

- Distributed computing coordinates networked nodes, while parallel computing performs multiple computations concurrently. Tightly coupled shared-memory systems are one form of parallel computing; distributed-memory clusters can also execute parallel programs.

- Distributed nodes typically have their own CPU, memory and storage. Parallel systems may use shared memory, distributed memory, or a combination.

- Shared-memory systems may have contention for shared resources; distributed-memory systems also face network, communication and coordination overhead.

- A failed shared resource can affect all users of it. A distributed node failure can also affect other nodes or the whole job; replication, redundancy and recovery determine how well failures are isolated.

  - The act of adding a complete node is called scaling out.

  - Removing a complete node is called scaling in.

- **Vertical scaling** is the process of adding or removing a component in only one computer node based on the workload of the system.

  - The act of adding a component in one node is called scaling up.

  - Removing a component in one node is called scaling down.

### 1.5 Eventually Consistent & Strongly Consistent

![课程插图](<assets/云计算金句/media/image26.png>)

- Eventually Consistent read might not always reflect the results of a recently completed write operation.

- Eventual Consistency across all copies of data will be reflected and updated after some time, meaning if you write data to a location and tries to read the data immediately in other locations, you may get stale data (data that is not up to date).

- A Strongly Consistent read will return a result that reflects all writes that received a successful response prior to reading it.

- Strong consistency is an observable read/write guarantee. It does not mean every physical replica is updated instantaneously in every location.

**2.1.1 Describe with examples of key words or codes the NINE steps you need to follow in CUDA (Compute Unified Device Architecture) C GPU (Graphics Processing Unit) programming.**

![课程插图](<assets/云计算金句/media/image31.png>)

1. **Define the kernel** — e.g. `__global__ void add();`
2. **Declare the main method** — e.g. `int main(void) { int a[N], b[N], c[N];`
3. **Allocate the memory on the GPU** — e.g. `cudaMalloc((void**)&dev_a, N * sizeof(int));`
4. **Fill the arrays `a` and `b` on the CPU** — e.g. `a[i] = -i;`
5. **Copy the arrays `a` and `b` to the GPU** — e.g. `cudaMemcpy(dev_a, a, N * sizeof(int), cudaMemcpyHostToDevice);`
6. **Launch the kernel on the GPU** — e.g. `add<<<N,1>>>(dev_a, dev_b, dev_c);`
7. **Copy the array `c` back from the GPU to the CPU** — e.g. `cudaMemcpy(c, dev_c, N * sizeof(int), cudaMemcpyDeviceToHost);`
8. **Display the results through the CPU** — e.g. `printf("%d + %d = %d\n", a[i], b[i], c[i]);`
9. **Free the memory allocated on the GPU** — e.g. `cudaFree(dev_a);`

**2.1.2 Write a GPU program using Compute Unified Device Architecture (CUDA) C environment that subtracts the float variable c from the sum of two float variables a and b ((a+b)-c) and then multiply the result by another float variable d (((a+b)-c)xd). Get the square root of the expression (sqrt(((a+b)-c)xd)) and assign the result to the float variable e and then print the result. Show all the necessary GPU and CUDA C steps that a normal GPU program will follow to execute and use comments in your program to show the steps (use a=3.0, b=7.0, c=2.0 and d=2 as your inputs)**

```cpp
#include <stdio.h>
#include <math.h>
#include <cuda_runtime.h>

// 1. Define the GPU kernel.
__global__ void add(float *a, float *b, float *c, float *d, float *e) {
    *e = sqrtf(((*a + *b) - *c) * *d);
}

int main(void) {
    // 2. Declare and initialize host data.
    float a = 3.0f, b = 7.0f, c = 2.0f, d = 2.0f, e;
    float *d_a, *d_b, *d_c, *d_d, *d_e;
    size_t size = sizeof(float);
    // 3. Allocate device memory.
    cudaMalloc((void **)&d_a, size);
    cudaMalloc((void **)&d_b, size);
    cudaMalloc((void **)&d_c, size);
    cudaMalloc((void **)&d_d, size);
    cudaMalloc((void **)&d_e, size);
    // 4. Transfer inputs from host to device.
    cudaMemcpy(d_a, &a, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_b, &b, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_c, &c, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_d, &d, size, cudaMemcpyHostToDevice);
    // 5. Launch one block with one thread.
    add<<<1, 1>>>(d_a, d_b, d_c, d_d, d_e);
    // 6. Copy the completed result back to host memory.
    cudaMemcpy(&e, d_e, size, cudaMemcpyDeviceToHost);
    // 7. Display the result: 4.000000.
    printf("Result e = %f\n", e);
    // 8. Release device memory.
    cudaFree(d_a); cudaFree(d_b); cudaFree(d_c);
    cudaFree(d_d); cudaFree(d_e);
    return 0;
}
```

CUDA 示例展示主要步骤，实际程序还应检查 CUDA API 与 kernel 的错误返回。

**2.1.4 Write a simple CUDA C program that will print the message “Welcome to GPU Programming World!”. Use myGPUKernel() as the kernel name for your CUDA C program and launch it using the \<\<\< \>\>\> delimiters to print the message “Welcome to GPU Programming World!” FIVE times in parallel (do NOT use any C iteration loop commands).**

```cpp
#include <stdio.h>
#include <cuda_runtime.h>

__global__ void myGPUKernel() {
    printf("Welcome to GPU Programming World!\n");
}

int main(void) {
    // One block with five threads: print five times without a C loop.

```

Map(productId, record) {
    emit(record.supplier, (record.price, 1));
}

// Optional local aggregation; input and output have the same value type.
Combine(supplier, values) {
    sum = 0;
    count = 0;
    for ((partialSum, partialCount) in values) {
        sum += partialSum;
        count += partialCount;
    }
    emit(supplier, (sum, count));
}

Reduce(supplier, values) {
    sum = 0;
    count = 0;
    for ((partialSum, partialCount) in values) {
        sum += partialSum;
        count += partialCount;
    }
    emit(supplier, sum / count); // Floating-point division
}

#### 3.1.6 What is the role of a Combiner, and how does it differ from a Reducer? Is its use optional?

- A Combiner is a mini-Reducer that processes the output of the Mapper before the data is sent to the Reducer.

- Its main function is to perform local aggregation of the data, which reduces the amount of data transferred over the network.

- The Combiner operates on the output of the Mapper and is applied before the shuffle and sort phase, whereas the Reducer works on the output after the shuffle and sort phase.

- A Combiner performs aggregation locally (for each Mapper's output), while a Reducer aggregates the data globally (after all Mappers have completed and the data has been shuffled).

- The use of a Combiner is optional in Map/Reduce jobs.

- For any of the following comments or any similar comment stating why Combiner is optional:

  - If specified, the framework will attempt to apply the Combiner, but it is not guaranteed to run or produce an output for every Mapper.

  - Developers can decide whether to use a Combiner based on the specific needs of the job and the nature of the data being processed.

- Caching in CDN involves storing copies of files or content in strategic/closer locations (nodes/servers).

- When a user requests content, the CDN directs the request to the nearest or most optimal node.

- Thereby reducing latency and bandwidth usage by serving the user with the cached content from a closer location.

#### 4.3.7 Explain two possible challenges faced by CDNs concerning caching and provide a solution for each.

**Challenges:**

- Cache Stale Content - serving outdated content if it is not synchronized with the origin server.

- Cache Busting – users or developers intentionally making URLs unique to bypass cache.

**Solutions:**

- Implement Time-To-Live (TTL) settings to ensure that cached content is refreshed after a specified duration.

- Use stable cache keys and controlled versioned URLs when static content changes; avoid unnecessary random query strings. Versioned static assets can safely use long cache lifetimes.

### 4.4 graph databases

#### 4.4.1 Define a graph in the context of graph databases. What are the key components of a graph?

- A graph is a data structure used in graph databases to model relationships between entities (nodes) through edges, enabling the representation of interconnected data.

- Nodes represent the entities or objects in a graph (e.g., people, places, or things).

- Edges represent the relationships between nodes (e.g., friendship between two people).

- They connect pairs of nodes and often include directionality (e.g., a one-way or two-way relationship).

- Both nodes and edges can have properties, which are key-value pairs that store additional information (e.g., a node for a person may have properties like name and age, while an edge may have properties like "since" for the duration of a relationship).

#### 4.4.2 Differentiate between directed and undirected graphs, providing an example for each.

- **Directed graph:** In a directed graph, edges have a direction, meaning the relationship between nodes goes one way.

  - Each edge points from one node to another.

  - Example: A Twitter follow relationship where user A follows user B but user B does not follow user A back is a directed graph.

  - The edge points from A to B.

- **Undirected graph:** In an undirected graph, edges do not have a direction, meaning the relationship between nodes is bidirectional.

  - The connection is mutual between the nodes.

  - Example: A Facebook friendship where both users A and B are friends with each other is an undirected graph.

  - The edge connects A and B with no specific direction.

#### 4.4.3 Describe the concept of property graphs. How do they enhance the representation of relationships in a graph database like Neo4j?

- A property graph is a type of graph where both nodes and edges can store additional data in the form of key-value pairs, known as properties.

- In property graphs, nodes represent entities and can hold properties (e.g., a person node can have properties like name and age).

- Edges, which represent relationships between nodes, can also hold properties (e.g., an edge between two people can store the property since to indicate the start of the relationship).

- Property graphs enhance the representation of relationships in databases like Neo4j by allowing both nodes and edges to carry detailed, context-specific information.

- This enables richer queries and more precise data analysis

#### 4.4.4 Explain why traditional NoSQL databases, despite being scalable, are not optimized for querying graph-based data. How do graph databases solve this issue?

- Traditional NoSQL databases (e.g., document stores, key-value stores) are designed to scale easily, handling large volumes of data across distributed systems.

- Despite their scalability, NoSQL databases are not optimized for graph-based queries because they store data in a non-connected format, requiring complex joins or multiple lookups to traverse relationships between entities, which results in inefficient querying.

- Graph databases (e.g., Neo4j) are specifically designed to handle graph structures where entities and their relationships are first-class citizens.

- They store data in a connected format, making traversals between nodes more direct and efficient.

- By storing nodes and edges as a graph structure, graph databases can perform fast, recursive traversals and relationship queries without needing costly joins, thereby solving the performance issues seen in traditional NoSQL databases.

#### 4.4.5 Describe the advantages of index-free adjacency in graph databases. How does this feature enable fast traversal of relationships?

- Index-free adjacency means that each node in a graph database directly references its adjacent nodes (neighbours) without needing an external index lookup.

- Unlike traditional databases that rely on indexes to locate relationships between entities, index-free adjacency eliminates this need, reducing the overhead of querying.

- Following one stored adjacency reference can avoid a global index lookup. Traversing a path or subgraph still costs time proportional to the relationships visited; a whole graph query is not constant-time regardless of its size.

- This feature enables fast and efficient traversal of relationships, making graph databases particularly effective for querying deep, complex, or highly interconnected data, such as social networks or recommendation systems.

#### 4.4.6 Explain why graph partitioning is necessary for processing large-scale graphs in distributed systems like Pregel or Apache Giraph.

- Graph partitioning is necessary because large-scale graphs can contain billions of nodes and edges, making it impractical to store and process the entire graph on a single machine.

- Partitioning breaks the graph into smaller subgraphs, which can be distributed across multiple machines, allowing parallel processing and more efficient use of distributed computing resources.

- By carefully partitioning the graph, the goal is to minimize the number of edges that cross between partitions, reducing the amount of communication between machines, which can be a major bottleneck in distributed systems.

- Partitioning enables systems like Pregel or Apache Giraph to scale horizontally, improving performance by enabling more efficient computation and faster execution times for large-scale graph analytics.

**4.4.6.1 In the context of graph databases, briefly explain the significance of an "edge" and provide an example where it can be practically applied in a social network graph.**

- In a graph database, an "edge" represents a relationship or connection between two nodes, which often represent entities.

- It enhances understanding of relationship dynamics and patterns within the network.

- **Practical Example:** In a social network graph, nodes might represent users, while an edge could represent a "friendship" relationship between them.

#### 4.4.7 Explain the role that graph partitioning plays in Pregel?

- Graph partitioning is splitting the graph data across the different distributed computing modules.

- It is necessary when a graph is too large to fit/processed on a single node.

- Graph partitioning determines which vertices and edges are stored on each worker.

- A good partition balances work and limits cross-worker communication.

- In Pregel’s vertex-centric model, communication with vertices on another worker generally requires network messages, rather than transparent shared-memory access.

- Fetching across the network is slower than loading from memory.

#### 4.4.8 What would happen if a graph was badly partitioned – why would it negatively impact performance?

- **Network Overhead:** Communication between vertices on different workers requires network messages. A poor partition may greatly increase this traffic.

- **Latency:** Fetching data across the network is significantly slower than loading it from local memory, causing a bottleneck.

#### 4.4.9 Describe the main concept behind Google’s Pregel. How does it parallelise graph computations? How does it minimise the need to send messages between nodes?

- **Vertex-Centric Parallelization:** Pregel parallelizes processing by treating each Vertex independently (processing them on different nodes simultaneously).

- **Minimizing Messages:** A partition that keeps communicating vertices together can reduce network traffic, and message combiners can reduce message volume where the operation permits it. Pregel’s default hash partitioning does not guarantee that connected vertices are colocated. [Pregel paper](https://research.google/pubs/pregel-a-system-for-large-scale-graph-processing/)
